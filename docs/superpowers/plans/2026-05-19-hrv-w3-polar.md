# HRV Module — W3: Polar Integration

> **For agentic workers:** REQUIRED: Use superpowers:subagent-driven-development (if subagents available) or superpowers:executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A member can connect their Polar account; HRV syncs automatically alongside WHOOP and Oura through the same daily cron and `/hrv` UI. The third (and final web-based) wearable provider.

**Architecture:** W3 is **additive**, and smaller than W2 — because W2's provider registry already made the OAuth callback, the connect action, and the sync cron provider-agnostic. W3 implements a `PolarProvider`, registers it, opens one small optional callback hook for Polar's required user-registration step, and activates the Polar row in the connect sheet. The `hrv_wearable_connections.provider` CHECK and `hrv_readings.source` CHECK already permit `polar` (migration 0032). **No migration needed.**

Polar's AccessLink API differs from WHOOP/Oura in three ways the plan handles explicitly:
1. **HTTP Basic Auth** on the token endpoint (`client_id:client_secret` base64 in the `Authorization` header) instead of form-body credentials.
2. **Tokens do not expire** — Polar issues no refresh token. `PolarProvider.exchangeCode` reports a far-future `expiresInSeconds` sentinel so the sync layer's expiry check never fires; `refreshTokens` throws (a safety net that is never reached).
3. **A required user-registration step** — after the token exchange, the user must be registered with the AccessLink app (`POST /v3/users`) before data can be pulled. This is exposed as a new **optional** `WearableProvider.registerUser?` method that the callback invokes if present (only Polar implements it).

**Tech Stack:** Next.js 16.2.4, React 19, Supabase, TypeScript 5, Vitest. No new dependencies.

**Spec:** [`docs/superpowers/specs/2026-05-15-hrv-module-design.md`](../specs/2026-05-15-hrv-module-design.md) revision 4.2 — §4, §11 (W3).

**Depends on (shipped):** W1 + W2 — `src/lib/hrv/wearables/{types,crypto,whoop,oura,sync,registry}.ts`, the provider-agnostic OAuth callback, connect action, and sync cron, `WearableConnectSheet.tsx`. Migrations 0031 + 0032.

## Prerequisite — not a code task (user action)

W3's live test needs a **Polar AccessLink app** registered at the [Polar admin portal](https://admin.polaraccesslink.com): it yields a **client ID** + **client secret**, and the app whitelists the redirect URI `http://localhost:3002/api/wearables/polar/callback`. These become env vars `POLAR_CLIENT_ID`, `POLAR_CLIENT_SECRET`. Tasks 1-5 build + unit-test with mocked Polar responses; only the live OAuth test (Task 6) needs the real app.

**Polar AccessLink API facts (verified 2026-05-19, polar.com/accesslink-api):**
- Authorize: `https://flow.polar.com/oauth2/authorization`
- Token: `https://polarremote.com/v2/oauth2/token` — **POST with HTTP Basic Auth** (`Authorization: Basic base64(client_id:client_secret)`), body form-encoded `grant_type=authorization_code` + `code` (+ `redirect_uri`). Response: `{ "access_token": "...", "token_type": "bearer", "x_user_id": 12345, "expires_in": <large or absent> }`. **No `refresh_token`.**
- Scope: `accesslink.read_all`
- API base: `https://www.polaraccesslink.com/v3`
- **User registration (required, once per user):** `POST https://www.polaraccesslink.com/v3/users` with the user's Bearer token, `Content-Type: application/json`, body `{ "member-id": "<our member UUID>" }`. A 409 Conflict means the user is already registered — treat 409 as success.
- **HRV endpoint:** `GET https://www.polaraccesslink.com/v3/users/nightly-recharge` with the user's Bearer token → a list of nightly-recharge records; each has a `date`, `heart_rate_variability_avg` (ms — Polar's nightly HRV), `heart_rate_avg`, `ans_charge`, `breathing_rate_avg`. **Verify the exact field names against the live Polar swagger during Task 1** — if `heart_rate_variability_avg` is named differently (e.g. `hrv_avg`), use the real name.
- Tokens **do not expire** unless revoked.

**Deviations / notes:**
- `PolarProvider.exchangeCode` sets `expiresInSeconds` to a far-future sentinel (`100 * 365 * 24 * 3600`) so the callback stores a `token_expires_at` ~100 years out and `syncConnection` never attempts a refresh. `refreshTokens` throws `Error("polar tokens do not expire")` — unreachable in practice.
- `WearableTokens.refreshToken` is `null` for Polar (the callback already handles a null refresh token — encrypts only when non-null).
- Polar nightly-recharge records are keyed by `date` (one per day). `fetchLatestHrv` maps `recordedAt` from that `date` (as an ISO instant, e.g. `<date>T00:00:00Z`) — stable per day, which the sync layer's same-day dedup keys on.

  - **(b) `exchangeCode(code, redirectUri)`** — POSTs to `https://polarremote.com/v2/oauth2/token`; assert the request carries an `Authorization: Basic <base64(client_id:client_secret)>` header and a form body with `grant_type=authorization_code`, `code`, **and `redirect_uri`** (Polar requires `redirect_uri` in the token request when it was sent on the authorize call — the callback always passes a `redirectUri`, so it must be in the body or Polar returns `invalid_grant`).   - **(e) `fetchLatestHrv(accessToken)`** — `GET /v3/users/nightly-recharge` with a Bearer header. Given a list of records, returns the most recent by `date`, mapped: `rmssdMs` ← `heart_rate_variability_avg`, `restingHeartRateBpm` ← `heart_rate_avg` (or `null` if absent), `recordedAt` ← `<date>T00:00:00Z`, `providerCalibrating` ← `false`. ## Chunk 2: Wire-up + UI

### Task 3: Callback invokes `registerUser`

**Files:** Modify `src/app/api/wearables/[provider]/callback/route.ts`

- [ ] **Step 1:** The callback is already provider-agnostic (resolves `providerImpl` via the registry, calls `exchangeCode`, etc.). Read the file to confirm variable names — the authenticated member is the `user` object from `supabase.auth.getUser()`; its id is **`user.id`** (there is no `memberId` variable). Add **one** additive step: after a successful `exchangeCode`, after the `hrv_wearable_connections` upsert, and **before** the best-effort initial-sync block, call:
  ```ts
  try {
    await providerImpl.registerUser?.(tokens.accessToken, user.id);
  } catch (e) {
    console.error("wearable registerUser failed", e);
  }
  ```
  A registration failure is logged but must NOT fail the callback — the connection row is already written; the daily cron retries. `registerUser` is optional on the interface, so `?.` no-ops for WHOOP/Oura. Do NOT add any `provider === "polar"` special-case — the optional-method dispatch keeps it provider-agnostic.
  **Consequence to expect (not a bug):** if Polar `registerUser` fails, the initial sync that follows also fails (Polar returns 403 on `nightly-recharge` for an unregistered user) — caught by the existing best-effort try/catch — and the daily cron keeps failing for that connection until registration succeeds. Acceptable; surfaces in Task 6's live test if Polar registration is misconfigured.
- [ ] **Step 2:** `npx tsc --noEmit && npm run lint` clean. `grep -i polar` is not required (the callback stays generic). Commit `feat(hrv): callback invokes optional provider registerUser`.
