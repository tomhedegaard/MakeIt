# HRV Module — W2: Oura Integration

> **For agentic workers:** REQUIRED: Use superpowers:subagent-driven-development (if subagents available) or superpowers:executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A member can connect their Oura Ring account; HRV syncs automatically alongside WHOOP through the same daily cron and the same `/hrv` UI. The second wearable provider.

**Architecture:** W2 is **additive** — the `WearableProvider` interface, the `hrv_wearable_connections` table (whose `provider` CHECK already allows `oura`), the `hrv_readings.source` enum (already allows `oura`), the OAuth callback route (`/api/wearables/[provider]/callback`, already dynamic), the sync cron, and the `/hrv` UI were all built provider-agnostic in W1. W2 implements an `OuraProvider`, introduces a small **provider registry** so provider resolution is no longer hard-coded to `whoop` in three separate files, opens the `oura` paths, and activates Oura in the connect sheet. **No migration is needed.**

**Tech Stack:** Next.js 16.2.4, React 19, Supabase, TypeScript 5, Vitest. No new dependencies.

**Spec:** [`docs/superpowers/specs/2026-05-15-hrv-module-design.md`](../specs/2026-05-15-hrv-module-design.md) revision 4.2 — §4 (wearable cloud APIs), §11 (W2).

**Depends on (shipped):** the W1 WHOOP integration — `src/lib/hrv/wearables/{types,crypto,whoop,sync}.ts`, `src/app/api/wearables/[provider]/callback/route.ts`, `src/app/api/cron/hrv-wearable-sync/route.ts`, `src/app/(app)/hrv/connect-actions.ts`, `src/components/hrv/WearableConnectSheet.tsx`. ## Prerequisite — not a code task (user action)

W2's live end-to-end test needs an **Oura developer app** (Oura Cloud → OAuth applications): it yields a **client ID** and **client secret**, and the app must whitelist the redirect URI `http://localhost:3002/api/wearables/oura/callback` (and a production URI later). These become env vars `OURA_CLIENT_ID`, `OURA_CLIENT_SECRET`. Tasks 1-5 build + unit-test with mocked Oura responses; only the live OAuth test (Task 6) needs the real app.

**Oura API facts (verified 2026-05-18, cloud.ouraring.com/docs/authentication):**
- Authorize: `https://cloud.ouraring.com/oauth/authorize`
- Token: `https://api.ouraring.com/oauth/token`
- Scope for sleep/HRV data: `daily` ("Daily summaries of sleep, activity and readiness"). **Verify during Task 1 against the live docs** — if the detailed `sleep` endpoint 403s on `daily` alone, also request `heartrate`.
- API base: `https://api.ouraring.com/v2`
- HRV endpoint: `GET /v2/usercollection/sleep?start_date=<YYYY-MM-DD>&end_date=<YYYY-MM-DD>` → `{ data: [ { id, day, average_hrv, lowest_heart_rate, bedtime_end, ... } ], next_token }`. `average_hrv` is the sleep-average HRV in ms (RMSSD-based); `lowest_heart_rate` is the resting-HR equivalent; `bedtime_end` is an ISO timestamp; `day` is the date.
- Access tokens carry `expires_in` (seconds; ~30 days). Server-side-flow refresh tokens are **single-use** — each refresh returns a new refresh token that must replace the stored one (same handling as WHOOP).
- Redirect URIs are an exact-match whitelist.

**Deviations / notes:**
- Oura has no WHOOP-style `user_calibrating` flag. `OuraProvider.fetchLatestHrv` maps `providerCalibrating: false` always, and returns `null` when the latest sleep document has no `average_hrv` (so the sync layer skips it).

Read `src/lib/hrv/wearables/whoop.ts` first — `OuraProvider` mirrors its structure (env-var credentials read at call time, `URLSearchParams` form-encoded token POSTs, Bearer `GET` for data, throw on non-ok responses, pure except for `fetch`).

Also: empty `data` → `null`; a sleep doc with `average_hrv: null` → `null`. If `data` has multiple docs, the **most recent** (latest `bedtime_end` / `day`) is used.
